# Warranty & RMA Operations
**Parent: 09-build-ota-factory-ci.md**

## 1. Scope and principles
Covers post-sale hardware warranty intake, triage, repair/refurbish, and re-issue for HALIDE REF-A/B retail and dogfood pools. Software issues ride the OTA train (A/B OTA with health gates, staged 1/10/50/100% per ch.09 §§4/26 — RMA never ships a one-off forked image to "fix" software). All diagnostics use redacted logs only (no IMSI/IMEI in tickets beyond last-4 + unit label; full serials in sealed inventory only). Turnaround target: triage verdict ≤3 business days, repair/replace ≤10 business days, tracked per §6-equivalent metrics in the RMA log.

## 2. RMA intake triage
Intake form (`support/rma-intake.md`, one per unit): unit label + serial, SKU, shipped version + current version (MANIFEST.lock SHAs where known), symptom (one line + first-seen date/build), repro steps tried (reboot, safe-mode-equivalent container restart, sideload-current-OTA y/n, factory-reset-consented y/n), accessory set returned (cable/charger/SIM-out — SIMs never returned; privacy rule stated on the form), data-backup consent + wipe authorization signature (no signature = no repair beyond non-destructive triage). On receipt: photo-in (unit + seals + traveler), power-on smoke (boot_completed y/n, `avbtool info` rollback + key state recorded — testkey on a shipped unit escalates to ch.09 §13-style incident, not a warranty repair), ticket opened in `support/rma-log.csv` (id, date-in, SKU, symptom class, triage owner, SLA clock start). SLA clock pauses only on documented customer-wait (awaiting wipe consent or ship-back address) with timestamps — pause-without-note counts against MTTR.

## 3. Software-vs-hardware fault isolation tree
Order is binding (cheap non-destructive first; destructive/flash steps only with wipe consent): (1) Reproduce on current release (OTA to latest staged-100% build via A/B path with health gates — sideload only if OTA path itself is the symptom; symptom gone after update = software-fixed, close as `SW-OTA-FIXED` with version pair recorded). (2) Safe-state reproduce (Android container restart + host-only boot per ch.04 §15 unsquashed/erofs split where applicable; radio-off vs radio-on split isolates modem per ch.07 §15 ladder; composer-killed vs running split isolates display per ch.10 §23). (3) Known-issue match (release notes KNOWN ISSUES + quarantine list ch.10 §§6/11 + DIG archive ch.10 §25 — match = `SW-KNOWN-<bug>`, unit returned with workaround card, no hardware touched). (4) Cross-unit reproduce (same build/SIM/band on lab spare per carrier-lab-handbook fixture rules; reproduces on spare = fleet/software-or-network, not this unit's hardware). (5) Factory-res flash (with consent: `factory/flash-station/` clean flash per ch.09 §16 + first-boot smoke; symptom survives clean flash + stock-oracle comparison where available = hardware-suspect, advance to bench). Skipping steps (straight to board-swap) invalidates the ticket — QA audits 10% of `HW-*` verdicts monthly for tree compliance; skip rate >10% triggers retraining, not punishment.

## 4. Refurbish-and-reflash flow with attestation
Hardware repair (board, display, battery, USB-C, buttons) follows per-SKU `hw/<sku>/repair.md` (torque values, adhesive cure times, ESD requirements — repair without the sheet open on the bench fails audit). Post-repair: full `factory/flash-station/` reflash to current release (never the version the unit arrived on if a newer staged-100% exists — refurb stock converges forward), AVB lock verified locked (`fastboot flashing get_unlock_ability` + `avbtool info` recorded), crypto-erase + first-boot smoke (boot_completed + MM register + 1 SMS loopback per ch.09 §9 health-gate trio), battery health readout recorded (`battery-health-aging-policy.md` capacity vs day-1 ±3% gate reused — degraded packs replaced, not shipped tired). Attestation (`support/rma-attest-<ticket>.md`, signed by tech + reviewer): hashes flashed, rollback index, key-id (release key fingerprint, verbal-check discipline per ch.09 §15 adapted: two humans read key-id aloud), prior-unit data disposition (`wiped <method> <date>` per ch.08 §21 + support-log-script redaction), seals/photos-out. Refurb units re-enter saleable pool only with attestation + 24h bench soak (suspend overnight + call-loop 10 cycles, ch.10 §7 scripts) green; otherwise parts-donor with data-bearing components destroyed (shred cert for storage, not trash).

## 5. Warranty-void conditions including unlock policy
Covered (24 months, battery 12 months at ≥80% health per battery-health sheet): manufacturing defects, buttons/ports under normal use, display delamination, modem/RF failure on approved FW, OTA-bricked units (A/B rollback + EDL unbrick per ch.09 §10 attempted first — bricked-by-our-OTA is always covered). Not covered (stated on the warranty card, enforced at triage with photo evidence): liquid ingress (LCI tripped + corrosion photo), crush/bend/thermal abuse (skin-temp logs where available + physical inspection), third-party board work, bootloader unlocked *at time of failure* for failures plausibly linked to unsigned boot (see unlock rule below — unlock alone does not void unrelated hardware claims).

Unlock policy (explicit, no gotchas): unlocking is permitted and documented (`runbook-recovery.md` unlock path); unlock sets a persistent flag + voids *software-brick* coverage past the EDL unbrick attempt (one good-faith unbrick per ticket, logged per ch.09 §10 EDL-use rule) and voids verified-boot-dependent security claims (attestation-key/rollback guarantees stated as not-applicable while unlocked — ch.08 §8 policy referenced on the form); relock to release keys + clean flash restores full warranty for unrelated hardware (relock verified by `avbtool` + attestation §4 — "was unlocked once" is not a permanent void). Testkey images never count as warranty firmware (testkey-never-ships per ch.09 §§3/11 — a unit arriving on testkey is treated as engineering-pool, routed to lab, not retail RMA).
